# Задача для coding-agent: адаптация Linet к Ryoku

Дата исходного аудита: 2026-11-11. Это исполняемая постановка задачи: исследуй,
внеси необходимые изменения в проект и пользовательскую интеграцию, проверь
результат. Не ограничивайся планом. Сначала восстанови основные функции, затем
реализуй минималистичный плагин. Разблокировку веди отдельным этапом ниже.

## Цель

Linet должен работать в Ryoku без зависимости от установленной/запущенной
caelestia: подключение Android, файлы, уведомления и ответы, буфер, Handoff,
экран телефона, заряд и управление из бара. Сохранить существующий протокол,
сопряжения, докачку файлов и совместимость Android. Не переписывать linet-core
или приложение телефона без доказанной необходимости.

## Обязательные правила работы

- Прочитай локальные AGENTS.md и инструкции проекта. Затем прочитай
  `~/.local/share/ryoku/rashin/AGENTS.md`, `desktop.md`, `ownership.md`, `user.md`
  и skill `ryoku` (сейчас `~/.codex/skills/ryoku/SKILL.md`). Для плагинов нужны
  `feature.md`, `plugins.md`, `build.md`; для окон — `wm.md`.
- Определи реальное состояние через `ryoku wm status`. Если Live=false, сначала
  проверь окружение и доступ к действующей сессии: это не доказательство отсутствия
  compositor. Не переключай сессию и не перезапускай её ради диагностики.
- Перед изменением конфигов спроси владельца через `ryoku owner <path>`.
  Используй команды владельца настройки; не редактируй shipped/generated/store.
  Пользовательские дополнения: `~/.config/hypr/user.lua`, `fish/user.fish`,
  `kitty/user.conf`. JSON-хранилища Ryoku менять через соответствующие CLI/GUI.
- Перед правками сохрани затрагиваемые конфиги. Не восстанавливай старый архив
  целиком поверх Ryoku. Не подключай старые модули caelestia целиком.
- До изменений изучи git status/diff; не трогай чужие изменения и не делай commit,
  push или публикацию плагина без отдельного запроса.
- Не выводи ключи, токены, .env, данные связки ключей и содержимое приватного
  состояния приложения. Не передавай рабочий код и секреты внешнему ds-agent.
- Не устанавливай и не обновляй весь рабочий стол попутно. Сохрани работающую
  оболочку; не запускай caelestia одновременно с Ryoku для «совместимости».
- Перед созданием плагина проверь текущий каталог Ryostore, built-ins и установленные
  плагины. Авторский плагин держи в каталоге, предусмотренном `ryoku plugin new`,
  обычно `~/Documents/ryoku-plugins/<id>/`; не пиши в установленную копию.
  В репозитории приложения храни документацию, исходный шаблон/средства установки
  при необходимости; не создавай две независимые редактируемые копии плагина.
- Плагин должен использовать публичный PluginKit, Theme/Motion, объявленные
  команды и возможности, argv вместо склеенного shell-кода. Валидируй его через
  `ryoku plugin validate`. Не публикуй через `ryoku plugin share`.
- Проверяй реальные сценарии. Отделяй автоматические проверки от ручных,
  недоступных без телефона/графической сессии. Не называй непройденную проверку
  успешной. В конце опиши изменения, проверки, ограничения и точный откат.

сопряжения. Сохрани права доступа. Не меняй идентичность ноутбука.

## 2. Приведи установку и запуск к единой схеме

Выбери и документируй один путь пользовательских бинарников. Обнови согласованно
установочные скрипты, unit, native messaging, desktop entries и Nautilus script.
Учти XDG-пути, абсолютные пути для GUI и PATH systemd. Не полагайся на PATH
интерактивного fish для сервиса. Переустановка должна быть идемпотентной,
а штатные cargo-команды не должны незаметно оставлять активную старую версию.

Запускай демон после передачи Wayland-окружения и готовности интерфейсов,
которым он регистрируется. Рассмотри привязку к ryoku-session.target с понятным
завершением при выходе. After= сам по себе не доказывает готовность D-Bus-сервисов.
Через Hub → Session доступен пользовательский автозапуск; для автоматизации
сначала изучи реально поддерживаемые команды, не выдумывай их.

Устрани гонки регистрации: трей сейчас регистрируется только один раз. Обработай
появление/смену владельца org.kde.StatusNotifierWatcher и перезапуск оболочки.
Проверь восстановление доставки уведомлений после смены сервера уведомлений.
Перезапуск Ryoku не должен требовать ручного перезапуска Linet.

## 3. Совместимость стандартных функций

Проверь существующие freedesktop Notifications и StatusNotifierItem в Ryoku.
Кнопки подтверждения сопряжения, ответ, открытие файла, закрытие уведомления
должны сохранять смысл. Не подменяй dismiss на action; проверь, что ответ не
удаляет телефонное уведомление ошибочно. Ryoku поддерживает actions; отображение
изображений было выключено настройкой, это не отсутствие поддержки сервера.

Буфер уже работает через wl-copy/wl-paste: не запускай старую историю cliphist
поверх новой истории Ryoku. Проверь текст, кириллицу, картинки и отсутствие эха.
Проверь Handoff и регистрацию расширения, не переиздавая и не переподписывая его
без необходимости. Исправь только обнаруженные проблемы.

Перенеси поведение scrcpy в пользовательский override Hyprland: Linet запускает
окно с заголовком «Телефон». Старый обработчик window.open/window.title делал
окно class=scrcpy плавающим и центрировал его: SDL задавал class поздно.
Не фиксируй aspect ratio и не затрагивай посторонние окна. Проверь действия
через launcher и файловый менеджер, не только из терминала.

## 4. Плагин Linet для QS Bar

Создай отдельный плагин `linet` через штатный механизм Ryoku. Не форкай
PhoneBridge/KdeConnectService и не эмулируй KDE Connect D-Bus API.

Минимальное представление: значок подключения и заряд телефона; без телефона —
понятное спокойное состояние, без ошибок в цикле. Панель по нажатию:
- имя/статус устройства, заряд/зарядка, выбор устройства при необходимости;
- отправить файлы;
- открыть экран телефона;
- выбрать Android-приложение;
- прогресс и итог текущих передач;
- понятное состояние «демон недоступен» и восстановление после его старта.

Уже есть D-Bus service org.linet.Daemon, path /org/linet/Daemon,
interface org.linet.Daemon1. Методы Devices, Battery, Stats, SendFile и другие
см. в коде; сигналы DevicesChanged, TransferProgress, TransferFinished.
`linetctl status` выдаёт JSON со связью; `stats --json` — статистику. Не парси
человеческий вывод `devices`, если можно использовать структурированный API.

Для первого варианта допустим ограниченный опрос структурированного API;
предпочитай события. Отдельного D-Bus сигнала батареи сейчас нет, а on_battery
не вызывает notify_changed: при необходимости добавь совместимое событие/API.
Новые списки/снимки/watch-режим должны иметь документированный JSON-контракт.
Не запускай высокочастотный опрос и не держи фоновые работы закрытой панели
без причины. Изменяющие действия — только по явному нажатию пользователя.

## 5. Экран ноутбука и виртуальный монитор

Сохрани текущий Hyprland backend vnc.rs, если проверка не выявит проблемы.
Он напрямую использует hyprctl monitors/output/eval и wayvnc. Не обещай niri
совместимость. В shared-коде нового плагина используй интерфейсы Ryoku, а
compositor-specific детали оставь в явно выделенном backend приложения.

Проверь mirror/extend, кириллицу, NVIDIA, масштаб, отказ/таймаут клиента,
завершение сервиса, сон, блокировку и hotplug/автомасштабирование Ryoku.
Headless-monitor не должен получать лишний бар/док или ломать основной экран;
при завершении созданный Linet output и wayvnc должны корректно убираться.
Не допускай продолжения захвата чувствительного экрана при блокировке.
Не открывай firewall глобально: сначала установи текущую сетевую политику.

## 6. Блокировка: обязательная совместимость, отдельная аутентификация

unlock.rs сейчас опрашивает IPC caelestia и затем pgrep hyprlock. Для Ryoku
это неверный источник состояния. Реализуй явный адаптер блокировки с понятными
возможностями: состояние, lock, поддержка authenticated unlock. Ryoku предоставляет
`ryoku-shell lock status` и `ryoku-shell lock`; точный вывод и ошибки перепроверь.
Недоступный backend не должен интерпретироваться как достоверно unlocked.
Автоблокировка должна пользоваться правильным backend и не спамить lock-запросами.

Сначала обеспечь корректные lock/status и честное «разблокировка этим backend
пока не поддерживается». Затем исследуй безопасную интеграцию телефона с qylock.
Он использует PAM, foreground login1 session, secure-lock proof и sleep guards.
Один лишь loginctl unlock-session может не снять Wayland-lock.

Запрещено добавлять открытый IPC unlock, убивать locker или посылать ему сигнал
в обход аутентификации. Не сохраняй и не передавай пароль пользователя.
Существующие qylock/PAM/shipped-файлы не патчить напрямую. Если нужен PAM-модуль
или изменение upstream Ryoku, подготовь отдельный reviewable patch/описание
протокола с проверкой подтверждения телефона, срока запроса, session binding,
повторного воспроизведения, отмены и гонок сна. Системную auth-интеграцию не
включай незаметно в базовый этап. Объясни конкретно, что ещё требуется.
Не блокируй пользователю рабочую сессию для unattended-теста; реальное снятие
блокировки проверяется с участием пользователя. Пароль должен работать всегда.

## Проверки и критерии готовности

- Запуск/выход/повторный вход, ровно один демон, правильные пути бинарников.
- Перезапуск Ryoku: восстановление трея/уведомлений/плагина без ручного restart Linet.
- Сопряжения сохранены; телефон подключается после перезапуска и сна.
- Файлы в обе стороны, докачка/целостность после обрыва; не регрессировать ветку
  fix/transfer-reliability.
- Текст/изображение буфера, уведомления с действиями и ответом, Handoff.
- scrcpy и app-mode, нормальное изменение размеров окна; VNC отдельно.
- Battery/connection/transfers в плагине, daemon-offline и reconnect.
- Lock/status/автоблокировка соответствуют Ryoku; phone-unlock либо проверенно
  реализован безопасным способом, либо явно обозначен отдельным незавершённым этапом.
- cargo test --workspace --locked; cargo clippy --workspace --all-targets --locked -- -D warnings;
  валидатор плагина. Новые тесты — для изменённой логики/API/гонок.
- Перед scripts/e2e.sh прочитай скрипт и его побочные эффекты; запускай изолированно.
  Он отключает unlock/autolock и не доказывает работу qylock или реального телефона.
- Не собирай Android ради чисто desktop-изменений. Если Android действительно
  менялся, используй документированный JDK 17 и соответствующие тесты.

Обнови README/DESIGN и установочные инструкции; перечисли файлы, что проверено
автоматически/вручную и что ещё требует телефона. Оставь команды установки,
обновления и отката, не включающие удаление пользовательских данных.
