## 1. Модель угроз, принятая в отчёте

| Доверие | Кто | Что может |
|---|---|---|
| Доверенный | Владелец ноутбука, процессы его сессии (в т.ч. на сессионной D-Bus) | всё |
| Полу-доверенный | **Сопряжённый телефон** (TLS-клиент с закреплённым отпечатком) | уведомления, буфер обмена, файлы, запрос VNC, Handoff, установку APK с подтверждением |
| Полу-доверенный | **Сопряжённый ноутбук** (с точки зрения телефона) | обратное направление: файлы, буфер, Handoff, ссылку `vnc://`, запрос включения ADB по Wi-Fi |
| Недоверенный | Всё в локальной сети, mDNS-ответчики, пакеты на UDP 47321/47322 | только попытки установить соединение / подсказать адрес |
| Недоверенный | Локальные процессы **других** пользователей | ничего (сессионная шина, каталоги 0700/0755 без group-write) |

Ключевое следствие: компромисс сопряжённого устройства — это **штатно сильный** противник. Всё, что он может, оценивалось по шкале «насколько это больше заявленных возможностей».

## 3. Находки

Отсортированы по риску. Для каждой: CWE, серьёзность, достоверность, расположение, сценарий, доказательство, исправление.

### F1. Устаревший `rustls 0.23.45` с известными уязвимостями

- **CWE-1104** (использование неподдерживаемых/устаревших компонентов) · **LOW–MEDIUM** · достоверность **высокая** (данные сканера, не гипотеза)
- **Где:** `Cargo.toml` (`rustls = "0.23"`), `Cargo.lock` → `rustls 0.23.45`; фикс — `0.23.46`

| ID | CVSS/Sev | Суть |
|---|---|---|
| GHSA-c8m5-c952-6cm4 | MEDIUM | `Debug`-форматирование TLS-сессии печатает master secrets и resumption PSK |
| GHSA-h2v8-394m-p7vv | LOW | brotli-декомпрессия сертификата → до 1 ГиБ памяти до проверки цепочки |
| GHSA-vp88-798v-h67f | LOW | ECH + rejection раскрывает буфер приложения внешнему серверу |
| GHSA-w44r-93j7-qv28 | LOW | неаутентифицированный `ServerHello` фиксирует выбор key-share → классический X25519 (harvest-now-decrypt-later) |

- **Сценарий эксплуатации в Linet:** не подтверждён ни для одной из четырёх.
  - Debug-вывод rustls-сессии не используется: логи идут через `tracing` и содержат только свои сообщения.
  - ECH не включён (`transport.rs` — TLS 1.3 + ALPN, без ECH-конфигурации).
  - Cert-compression/decompression в конфигурации Linet не активируется.
  - Последняя уязвимость даёт только потерю пост-квантовой стойкости записанных сессий, без компрометации ключей и без обхода аутентификации.
- **Исправление:** `cargo update -p rustls --precise 0.23.46` (и прогнать `cargo test`; `quinn`/`ring` совместимы).
- **Почему всё равно в отчёте:** это единственное расхождение между «сканер чист» и «сканер нашёл», и держать TLS-стек в актуальном состоянии дешевле, чем объяснять CVE в зависимостях.

### F2. Телефон открывает URI, присланный ноутбуком, без проверки схемы

- **CWE-939** (некорректная авторизация внешнего ресурса) / **CWE-749** · **LOW–MEDIUM** · достоверность **высокая**
- **Где:** `android/app/src/main/java/org/linet/LaptopScreen.kt:35`

```kotlin
activity.startActivity(Intent(Intent.ACTION_VIEW, Uri.parse(url.getOrThrow())))
```

Источник `url`: `crates/linet-ffi/src/lib.rs:337` — `Message::VncResult { url, error } if error.is_empty() => Ok(url)`. Значение приходит по сети от ноутбука; схема не проверяется. Честный демон строит `vnc://{ip}:{PORT}?…` (`crates/linetd/src/vnc.rs:119`), но контракт протокола этого не требует, а клиент не проверяет.

**Асимметрия с уже закрытым:** для Handoff проверка схемы есть на обеих сторонах — `crates/linetd/src/mirror.rs:51` и `Handoff.kt` (`if (uri.scheme != "https" && uri.scheme != "http") return`).

- **Сценарий (2 шага):**
  1. Ноутбук (или процесс, получивший доступ к `org.linet.Daemon` / к ключу устройства) в ответ на `VncRequest` посылает `VncResult{ url: "intent://…" }` с `android.intent.action.VIEW`.
  2. Телефон исполняет implicit intent: `intent://…#Intent;component=<любой экспортированный компонент>;S.<extra>=…;end`, `market://`, `file://` и т. п. — открываются чужие Activity/настройки, выполняется deep-link в приложении (в т.ч. финансовом).
- **Доказательство:** данные проходят путь `VncRequest → daemon.on_vnc_request → VncResult{url} → FFI → LaptopScreen.open` без единой проверки префикса; `Uri.parse` + `ACTION_VIEW` — единственная точка решения.
- **Исправление (одна точка, в FFI, чтобы правило было единым):**

```rust
// crates/linet-ffi/src/lib.rs, request_vnc
match reply {
    Message::VncResult { url, error } if error.is_empty() => {
        if !url.starts_with("vnc://") {
            return Err(LinetError::Failed("некорректная ссылка VNC".into()));
        }
        Ok(url)
    }
    ...
}
```

и дублирующая проверка в UI (`if (!raw.startsWith("vnc://")) { Linet.client(activity).stopVnc(); return }`).

### F3. `ShareActivity` экспортирована: любое приложение может положить текст в буфер ноутбука

- **CWE-926** (экспортированный компонент) + **CWE-345** · **LOW** · достоверность **высокая**
- **Где:** `android/app/src/main/AndroidManifest.xml` (`ShareActivity`, `exported="true"`, `SEND`/`SEND_MULTIPLE`), `ShareActivity.kt:22-30`

```kotlin
val text = intent.getCharSequenceExtra(Intent.EXTRA_TEXT)?.toString()
...
if (intent.action == Intent.ACTION_SEND && uris.isEmpty() && !text.isNullOrEmpty()) {
    ...
    ClipboardSync.send(this, text)   // → wl-copy на ноутбуке
}
```

- **Сценарий:** установленное на телефоне приложение делает `startActivity(ACTION_SEND, EXTRA_TEXT="<свой адрес получателя>")` на `org.linet/.ShareActivity`. Без действия пользователя (кроме краткой прозрачной Activity) текст оказывается в буфере ноутбука — классическая подмена адреса кошелька/реквизитов, рассчитанная на то, что пользователь вставит его из буфера.
- **Оговорка (честности ради):** `ClipboardSync.send` показывает Toast «Скопировано на ноутбук», то есть полностью незаметным это не является. Поэтому LOW, а не MEDIUM.
- **Файлы при этом защищены корректно:** `Transfers.isForeignContent` отбивает `file://` и собственный FileProvider (`org.linet.clip`), поэтому вытащить приватные файлы Linet через «Поделиться» нельзя.
- **Исправление (по возрастанию строгости):**
  1. Заменить Toast на уведомление с содержимым (первые символы), чтобы подмена была заметна.
  2. Принимать «голый» текст только от вызывающего с ожидаемым `callingPackage` (например, браузер по умолчанию), для остальных — требовать вложение.

### F4. Приём файла без подтверждения + кнопка «Открыть» = запуск `.desktop`

- **CWE-829** (включение функциональности из недоверенной области) · **LOW** · достоверность **средняя** (нужен клик пользователя)
- **Где:** `crates/linet-core/src/files.rs:126-184` (автоприём от сопряжённого устройства), `files.rs:479` (`sanitize` сохраняет расширение), `crates/linetd/src/dbus.rs:244` (`xdg_open(&path)`)

- **Сценарий (3 шага):**
  1. Скомпрометированный телефон отправляет `photo.desktop` (или `.html`, `AppImage`) — файл принимается автоматически и попадает в `~/Downloads/Linet`.
  2. Ноутбук показывает «Файл от <имя>: photo.desktop» с кнопками «Открыть» и «Папка».
  3. Пользователь нажимает «Открыть» → `xdg-open` исполняет `.desktop`.
- **Почему не выше:** контент приходит от устройства, которому пользователь уже разрешил присылать файлы; барьер — один клик. Но кнопка «Открыть» — это фактически «запусти присланное», и она этого не сообщает.
- **Исправление:** для полученных из сети файлов не вызывать `xdg_open` напрямую: открывать каталог (`path.parent()`), либо для расширений `desktop|sh|bash|AppImage|html|xhtml|js` показывать «Показать в папке» вместо «Открыть».

### F5. Сопряжённый пир может раздуть память демона до ~1 ГиБ и занять все слоты приёма

- **CWE-400** (неконтролируемое потребление ресурсов) · **LOW** · достоверность **средняя**
- **Где:** `crates/linet-core/src/frame.rs:10` (`MAX_FRAME = 16 << 20`), `crates/linet-core/src/session.rs:56` (`mpsc::channel(64)`), `crates/linet-core/src/files.rs:32` (`MAX_PENDING = 64`), `files.rs:194` (`active` держится, пока жив поток)

- **Механика:** чтение управляющего потока декодирует кадр целиком и затем ждёт освобождения очереди; при 64 слотах в очереди в полёте оказывается до ~65 тел по 16 МиБ ≈ 1 ГиБ. Параллельно до 64 «висящих» `FileOffer` держат `.part` и слоты, пока соединение открыто (idle-таймаут — 30 минут, `transport.rs:19`).
- **Почему LOW:** нужен уже сопряжённый пир. Но именно против этого написан `tune_malloc()` в `main.rs` (борьба за RSS) — то есть цель по памяти обходится по другому каналу.
- **Исправление:** отдельный лимит для `ClipboardImage` (12 МиБ, `proto.rs:145`) вместо общего 16 МиБ и уменьшение `MAX_FRAME` до 1 МиБ для остальных сообщений; ограничение числа одновременных `active`-приёмов с одного пира (например, 4).

### F6. D-Bus `send_file` отдаёт любой файл пользователя — примитив exfiltration для песочниц (INFO, by design)

- **CWE-862** (отсутствие проверки авторизации) · **INFO** · достоверность **высокая**
- **Где:** `crates/linetd/src/dbus.rs:76-82`

```rust
async fn send_file(&self, id: &str, path: &str) -> fdo::Result<u64> {
    let path = Path::new(path);
    if !path.is_absolute() { return Err(...); }
    self.daemon.send_file(id, path, None).await.map_err(err)
}
```

Любой абсолютный путь, проверяется только `is_absolute()`. На сессионной шине метод доступен всем процессам пользователя, включая приложения в песочницах, которым выдан доступ к шине (`--socket=session-bus` у Flatpak и т. п.), но не к файловой системе.

- **Почему INFO:** ровно та же модель, что у большинства десктопных демонов («сессионная шина = доверие пользователя»). Но если хочется сузить поверхность — это готовый путь «песочница → эксфильтрация `~/.ssh/id_rsa` на телефон».
- **Исправление (опционально):** peer-credentials через `zbus` + белый список меток AppArmor/cgroup, либо подтверждение в уведомлении для путей вне `$HOME/{Downloads,Documents,Desktop,Pictures}`.

## 4. Ложные срабатывания и отброшенные гипотезы

### 4.1 `gitleaks`: «Generic API Key» в `extension/manifest.json:39`

Строка `"key": "MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8A…"` — это **публичный** RSA-ключ (SPKI, `SubjectPublicKeyInfo`) для фиксации ID расширения в AMO. Секретом не является, утечки нет; ключ присутствует и в HEAD, и в коммите `8a1579d`. Правило `generic-api-key` срабатывает по энтропии на длинной base64-строке.

**Действие:** ничего. При желании — `# gitleaks:allow` в конфиге по fingerprint `…:extension/manifest.json:generic-api-key:39`.

### 4.2 `write_private`: предсказуемый `.tmp` и следование симлинкам

`crates/linet-core/src/store.rs:100-115` открывает `<path>.tmp` с `create(true).truncate(true)` без `O_NOFOLLOW`/`O_EXCL`. Теоретически — симлинк-атака «чужой пользователь подкладывает `peers.tmp` → запись в чужой файл».

**Отброшено:** каталоги (`~/.local/share/linet`, `$XDG_CONFIG_HOME`, `$XDG_RUNTIME_DIR`) не доступны на запись другим пользователям, поэтому подложить симлинк некому. Единственный путь, где каталог мог бы быть общим, — fallback `std::env::temp_dir()` в `crates/linetd/src/vnc.rs:82` при незаданном `XDG_RUNTIME_DIR`; под `systemd --user` переменная всегда задана.

**Замечание к гигиене (не уязвимость):** стоит добавить `O_EXCL`/`O_NOFOLLOW` и класть временный файл в подкаталог `0700` — это дешевле, чем каждый раз доказывать недостижимость.

### 4.3 Ответ на запрос можно подделать, зная `id`

`Session::dispatch` (`session.rs:91-96`) доставляет ответ по `reply_to` без проверки отправителя — но отправитель и так аутентифицирован закреплённым сертификатом, а `id` выделяются локально с шагом 2. Подделка возможна только сопряжённым пиром в свой же сеанс — не даёт ничего нового.

### 4.4 `sanitize()` и Unicode/bidi

`sanitize` (`files.rs:479`) отсекает пути, control-символы и ведущие точки, ограничивает 200 символами. RTL-override (`U+202E`) не фильтруется, но это влияет только на отображение имени в уведомлении, не на путь; реального переименования/обхода каталога нет.

### 4.5 `random_password()` в `vnc.rs`

`ALPHABET` 55 символов, `byte % 55` даёт смещение ≈3 % (символы с индексами < 36 чуть вероятнее). Энтропия остаётся ~90 бит при одноразовом пароле и guard’е по времени — не находка. При желании — `rand::distributions::Uniform`.

### 4.6 `rollback-ryoku.py` и `tarfile`

`home / name` берётся из `integration-after.json` внутри каталога бэкапа. Если подсунуть чужой бэкап, имена вида `../…` прошли бы. Скрипт запускается пользователем вручную над собственным бэкапом, поэтому — гигиена: добавить проверку `(home / name).resolve().is_relative_to(home)`.

## 5. Проверено и найдено безопасным

Ниже — то, что просмотрено по data-flow и **не** дало находки. Это важная часть результата: большая часть кода уже написана защитно.

**Передача файлов** (`crates/linet-core/src/files.rs`)
- `sanitize`: basename (`rsplit(['/', '\\'])`), удаление control-символов, `trim_start_matches('.')`, лимит 200, пустое → `file`.
- `.part`-имя = SHA-256(fingerprint_пира ‖ name ‖ size ‖ sha256)[..12], т. е. не угадывается и не пересекается между пирами.
- `persist`: `hard_link` (атомарно, без перезаписи) + fallback `rename` при отсутствии hardlink; коллизии → `name (1)`, `name (2)`.
- Целостность: обязательный SHA-256 для докачки, `set_len(offset)`, хеш префикса перед дозаписью, `done == total`, отказ при `done > total` и `offset > size`.
- Лимиты: 8 ГиБ на файл (`DEFAULT_MAX_SIZE`), `MAX_PENDING = 64`, `OFFER_TTL = 60 c`, `PART_TTL = 48 ч`, `prune_parts` не трогает зарезервированные пути.
- Повторный поток без принятого предложения и повторный `active` — отклоняются.

**Криптография и транспорт**
- TLS 1.3 only (`transport.rs:29`), ALPN, `verify_tls12_signature` → ошибка.
- Пиннинг сертификата по SHA-256 в обе стороны: `PinnedClientVerifier` (`tls.rs:44`) и `PinnedServerVerifier` (`tls.rs:94`); аутентификация по ключу, не по CA/hostname.
- Сопряжение: одноразовый 16-байтный секрет из `SystemRandom`, HMAC-SHA256 с доменом `linet-pair-v1`, привязка отпечатка клиента, проверка `ring::hmac::verify` (constant-time), окно 120 с, **обязательное подтверждение человеком** в уведомлении (`PAIRING_CONFIRM = 60 c`), приглашение одноразовое (`window.take()`).
- Подсказки адреса (`hint.rs`): Ed25519-подпись ключом ноутбука, проверка `ip == src`, `|ts − now| ≤ 300 c`, `port != 0`, сертификат берётся из закреплённой записи.
- Идентичность: ключ пишется `0600` (`write_private`), `reset_key` — HMAC от ключа (для stateless reset).
- Сторонние примитивы: ring / rustls / rcgen, ни одной самодельной схемы.

**Инъекции**
- Все внешние команды — `Command::new(...).args(...)`, без `sh -c` с подстановкой данных: `adb`, `scrcpy`, `hyprctl`, `wayvnc`, `openssl`, `wl-copy`, `wl-paste`, `ryoku-shell`, `fuzzel/rofi/zenity`, `notify-send`, `xdg-open`.
- В `wl-paste --watch sh -c` подставляются только константные скрипты (`TEXT_SCRIPT`, `IMAGE_SCRIPT`).
- `install-user.py`: `.desktop` собирается с экранированием `\`, `"`, `` ` ``, `$`, `%`; nautilus-скрипт — через `shlex.quote`; в systemd-юнит путь подставляется через `json.dumps` + экранирование `%` как `%%`.
- `setup-ryoku.py`: перед применением конфига — `luac -p` (синтаксическая проверка), запись через `ryoku owner`.

**Уведомления и рабочий стол**
- `escape_body` (числовые HTML-сущности для HTML **и** Markdown) + `neutralize_plain` для `app`/`summary`; учитывается capability `body-markup`.
- Обработчики кликов привязаны к владельцу имени на шине и к «поколению» сервиса уведомлений; после смены владельца обработчики сбрасываются — подделать `ActionInvoked`/`NotificationClosed` чужому отправителю нельзя.
- Кэш иконок: имя файла = `package`, отфильтрованный до `[A-Za-z0-9._]` — обхода каталога нет. `MAX_SHOWN`/`MAX_HANDLERS` = 200, «старые» вытесняются.
- Handoff: только `http(s)` на обеих сторонах; `xdg_open` получает только URL.

**VNC**
- Запуск только при `LockState::Unlocked` (fail-closed: `Unknown` → отказ), повторная проверка каждые 250 мс и по `prepare_for_sleep`.
- Одноразовый пароль, `enable_auth=true`, TLS-ключи и RSA-ключ 2048 (0600), слушается только адрес в сети телефона (`local_ip_towards`), `CONNECT_TIMEOUT = 60 c`, `generation` защищает от «протухших» guard-задач, конфиг и сокет удаляются при остановке.
- При уходе телефона (`run_session` → gone) — `vnc.stop()`.

**Автоблокировка/разблокировка**
- `Unlocker::attempt` всегда `bail!("…authenticated unlock… пока не поддерживается")`; `lock_status` отдаёт `authenticated_unlock:false`. Неаутентифицированного пути разблокировки нет.
- `autolock` только блокирует, только после `IDLE_AFTER`, только если телефон был рядом; `Unknown`-состояние блокировку не инициирует и не отменяет.
- На телефоне: кнопка «Разблокировать» — `setAuthenticationRequired(true)` (API 31+), проверка `KeyguardManager.isDeviceLocked` **в момент** подтверждения, одноразовое решение по `id` в `pending`.

**Android-периметр**
- `allowBackup="false"`.
- `exported="false"`: `LinetService`, `UnlockReceiver`, `UnlockActivity`, `ClipboardActivity`, FileProvider.
- `NotifyListener` защищён `BIND_NOTIFICATION_LISTENER_SERVICE`, `ClipboardTile` — `BIND_QUICK_SETTINGS_TILE`.
- `BootReceiver` слушает только protected-броадкасты (`BOOT_COMPLETED`, `MY_PACKAGE_REPLACED`).
- Все `PendingIntent` — `FLAG_IMMUTABLE` (+`FLAG_UPDATE_CURRENT`), данные в extras, не в `data`-URI, кроме retry-save, который проверяет путь.
- `Transfers.retrySave`: `canonicalFile.parentFile` обязан быть `filesDir/incoming` или `cacheDir/incoming`, иначе `require` падает.
- `Transfers.send`: `require(isForeignContent)` — `file://` и собственный `org.linet.clip` отбиваются.
- Приём файлов: `MediaStore` с `DISPLAY_NAME`/`RELATIVE_PATH`, откат через `resolver.delete` при ошибке, `IS_PENDING` снимается после копирования.
- `Handoff.kt`: `Uri` пропускается только для `https`/`http`.
- `ScreenShare`: включается только по запросу ноутбука, только в Wi-Fi, отключается при разрыве связи (`disconnected`), требует `WRITE_SECURE_SETTINGS` и подтверждения ADB-ключа на телефоне.
- «Снять ограничение батареи» / автозапуск — только через системные экраны, без `WRITE_SETTINGS`-трюков.

**Прочие мелочи, проверенные и признанные нормальными**
- `frame::read` корректно обрабатывает `FinishedEarly(0)` и проверяет длину до аллокации (остаточный риск — F5).
- `PeerStore::find` по префиксу возвращает `None` при неоднозначности (в т.ч. для пустой строки).
- `downloads_dir()` уважает `user-dirs.dirs`, подстановка `$HOME` есть; `${HOME}` не поддерживается — косметика.
- `identity.load_or_create` не падает при отсутствии каталога, ключ `0600`, сертификат публичный.
- Корректная обработка обрыва: `SEND_ATTEMPTS = 3`, `RESUME_WAIT = 120 c`, `wait_new_session` по `watch`-каналу, а не опросом.
- Каких-либо секретов в репозитории нет: `identity.key.der`, `signing.properties`, `.jks`, `amo.env` — вне git.

## 8. Итог

- **Критических и высоких уязвимостей не найдено.** Ни одного пути, дающего RCE/утечку/обход аутентификации противнику без доверия (сеть, mDNS, чужой пользователь).
- **Одна реальная слабость проектирования** — отсутствие проверки схемы при открытии ссылки VNC на телефоне (F2): единообразие с Handoff нарушено именно там, где приходит управляемое значение.
- **Три находки уровня LOW** (F3–F5) — про подмену буфера, «запуск присланного файла одним кликом» и исчерпание памяти сопряжённым пиром.
- **Остальное — гигиена:** устаревший `rustls` (F1), отсутствие `O_EXCL` в атомарной записи (4.2), доверие к сессионной шине (F6).
- **Сканеры:** чисто, кроме `rustls`; `semgrep`/`nodejsscan` для Rust/Kotlin почти слепы, поэтому основной вес — в ручном разборе. Единственная находка `gitleaks` — публичный ключ расширения, ложное срабатывание.

Отчёт подготовлен без изменения файлов проекта; настоящий документ — единственный добавленный файл.
